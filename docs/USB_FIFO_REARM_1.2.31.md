# USB audio FIFO stall and narrow re-arm — 1.2.31

On 1.2.30, the user again reported that Windows held the microphone open without receiving audio. The device's one-shot containment had already rebooted the MCU by the time HTTP was queried. The read-only post-reboot state and persisted first audio fault are saved in `.cache/incident-20260930-repeat-{status,guard,audio,logs}.json`.

The pre-reboot fault was on UAC IN endpoint 3. It had a pending 64-byte transfer (`DIEPTSIZ=0x80040`), an enabled endpoint (`DIEPCTL=0x80c48040`), an asserted FIFO-empty interrupt flag (`DIEPINT=0x2090`, TXFE bit 7), and an empty FIFO with 47 free words (`DTXFSTS=47`). Yet `DTKNQR4_FIFOEMPTYMSK=0`, so that TXFE interrupt was masked. The most recent USB audio completion was 2278 ms before this fault snapshot. These registers are sampled sequentially and do not by themselves prove the exact timing of a race, but they identify a missing FIFO-empty wakeup as a concrete explanation for the stalled transfer.

The bundled ESP32-S3 TinyUSB DCD is a prebuilt archive. The [upstream TinyUSB 0.15.0 `dcd_esp32sx.c`](https://github.com/hathach/tinyusb/blob/0.15.0/src/portable/espressif/esp32sx/dcd_esp32sx.c) enables an endpoint bit in `dtknqr4_fifoemptymsk` while scheduling a transfer and clears it in the IN ISR after writing all bytes, using separate read/modify/write operations. A lost update between those contexts is a plausible cause; exact source equivalence to the bundled object and the specific interleaving are not established by this snapshot.

Version 1.2.31 adds a narrow re-arm in the serialized TinyUSB service task. After 30 ms without a completion, it checks that this UAC endpoint is busy and enabled, its TXFE status is asserted, exactly one 64-byte block remains, the FIFO has room, and the endpoint's FIFO-empty mask bit is off. Only then does it set that bit again. It retries at most every 40 ms; the existing 500 ms full-recovery path remains if progress does not resume. `/api/audio` exposes `usb_fifo_rearms` and `usb_fifo_rearm_completions`.

Build and OTA boot passed. Ten Windows WinMM open/capture/close cycles all captured roughly 39–44 KB, completed 607–654 packets per cycle, and recorded zero USB recoveries or failed submissions. During that test, the new guard re-armed once and a subsequent transfer completion was observed (`usb_fifo_rearms=1`, `usb_fifo_rearm_completions=1`). This shows the condition occurs and transfer progress followed a re-arm, not that the intermittent user-visible failure has been eliminated. Physical voice capture and extended use still need observation.
