# USB audio stall and controlled restart on 1.2.43

The user reported that audio stopped reaching the application. The first status read found firmware 1.2.43 at 50 seconds uptime, `boot_reset_reason=3`, and `boot_usb_recovery_restart=true`. This confirms the firmware's deliberate one-shot restart after repeated USB audio recovery failures, rather than an unexplained reset or an Alt key remaining held.

The fresh NVS audio-fault snapshot was captured at 15,198,487 ms of the previous boot (about 4 h 13 min). The last completed USB audio transfer was at 15,192,924 ms, a 5,563 ms gap. Endpoint 3 IN had an enabled endpoint (`DIEPCTL=0x80c48040`), a pending 64-byte transfer (`DIEPTSIZ=0x80040`), FIFO-empty mask set (`0x8`), no FIFO-empty interrupt (`DIEPINT=0x2010`), and 35 free FIFO words. This matches the unhandled stall class seen on 1.2.31: the targeted FIFO-mask re-arm cannot help when the mask is already set and TXFE is not asserted. The HID trace also contains three report completion timeouts in the previous boot, though this snapshot does not prove they caused the audio stall.

Further register decoding: `GINTSTS=0x04108028` has bit 20 (`INCOMPISOIN`, incomplete isochronous IN transfer) set, while `GINTMSK=0x208c3c16` has bit 20 masked. `DIEPINT=0x2010` has an IN-token-while-TxFIFO-empty indication and NAK, but no transfer-complete or FIFO-empty indication. This is consistent with an isochronous IN transaction left pending without a path to finish it. It does not reveal the precise earlier software/hardware interleaving.

The custom UAC `SET_INTERFACE` handler currently only flips `s_uac_streaming` for alt 0/1; it does not abort an in-flight isochronous transfer on alt 0. Frequent application capture open/close cycles therefore raise a credible stale-transfer risk. The linked Arduino TinyUSB archive contains the older `dcd_esp32sx` driver without an individual endpoint-close or ISO-activate primitive; a safe endpoint abort needs a driver/stack change. Current upstream TinyUSB's vendor alternate-setting implementation explicitly aborts an in-flight ISO transfer when leaving an altsetting, and its release history includes fixes for DWC2 ISO IN transfers with `bInterval > 1` (this microphone uses `bInterval=2`). Those upstream facts support the mechanism but do not prove that the last altsetting transition was the immediate trigger here; the pre-fault transition history was not persisted.

After restart, BLE connected and three voice holds produced 161, 93, and 416 decoded BLE audio frames, with 1,265, 753, and 3,189 completed USB audio packets respectively. Their PCM had nonzero samples, and the Right Alt release was transmitted each time. The new boot had zero USB recoveries and no held modifier at the first check. This proves audio resumed at the device-to-USB layer; it does not prove the speech application reopened the new capture stream after USB re-enumeration.

Raw post-restart `/api/status`, `/api/guard`, `/api/audio`, and `/api/logs` responses are saved in `.cache/incident-20261001-usb-restart-1.2.43/`. The pre-restart ordinary logs are volatile; the NVS snapshot is the durable evidence.
