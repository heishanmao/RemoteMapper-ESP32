# Voice window ends but recognizes no speech — 1.2.34 investigation

On 1.2.33, the user reported that Windows dictation ended on key release but recognized no speech. In a synchronized approximately 5.3-second physical hold, the remote delivered 342 complete ADPCM frames (~66.5 fps during the main five-second window). The device decoded and enqueued 82,079 samples, and the USB IN endpoint completed 2,555 additional 64-byte transfers while the host had the audio interface active. The ring consumer advanced by 81,472 samples, with zero USB recoveries and no HID release pending. The release report completed and Windows set UAC alt 0. The spectral probe observed nonzero input energy, but it runs before postprocessing and does not prove that the final USB PCM was nonzero.

An independent Windows WinMM recording attempt could not open the microphone while this dictation workflow was active (`waveInOpen` error 1). No waveform was captured, so there is no direct content-level proof of what Windows heard. The device-side transport counters do not explain why Windows speech recognition produced no text.

Version 1.2.34 adds cumulative, read-only diagnostics for PCM submitted to the USB audio endpoint: `usb_pcm_samples`, `usb_pcm_nonzero`, `usb_pcm_absolute_sum`, and `usb_pcm_peak` on `/api/audio`. Audio is not stored. The normal audio format and delivery logic are unchanged. Comparing these counters before and after a physical voice hold distinguishes a stream of digital silence from nonzero audio that Windows fails to recognize. A physical test on 1.2.34 is pending.
