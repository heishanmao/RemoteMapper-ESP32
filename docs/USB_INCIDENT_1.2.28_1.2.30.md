# USB microphone incident: 1.2.28 capture and 1.2.30 containment

The user observed Windows holding the microphone open with no audio stream. Device HTTP stayed responsive and BLE reported connected, so this was not an MCU crash. Read-only snapshots were saved in `.cache/incident-20260930-usb-recovery/` before the authorized software restart.

The 1.2.28 snapshot showed 81 USB recoveries and 22 forced releases. The last fault was audio: UAC IN3 remained busy with no transfer completions. At that snapshot, `audio_completed=6429`, `audio_failed=0`, `audio_last_complete_ms=6792483`, and the repeated host `SET_INTERFACE alt=1` appeared about two seconds after each soft re-enumeration. Each session then produced no completion for 500 ms. The log shows recovery #75–#81 every ten seconds; later the device saw USB STOPPED and could not send a pending HID release. HID had 88 completion wait timeouts, 192 not-ready observations, and no submission rejections. These later HID failures may be downstream of USB reset churn; the first failing transfer was not retained, so the exact initiating cause remains unknown.

The saved UAC register snapshot had `fifo_empty_mask=0x8`, `diepctl=0x80c48040`, `dieptsiz=0x80040`, `diepint=0x2010`, and `dtxfsts=0x23`. These are sequential read-only observations, not an atomic snapshot. The FIFO-empty mask bit was **set**, so this incident does not establish that the previously suspected lost-mask-bit race caused the audio stall. Upstream reports of ESP32-S3 IN endpoints sticking are relevant background, not proof of this incident's cause.

After a web-requested MCU restart, 1.2.28 returned with BLE connected, zero new recoveries, USB audio completions advancing, and no pending HID report. The user confirmed a new voice press/release worked and Windows ended recognition. That shows a full MCU reset cleared the observed state, while the previous soft USB re-enumerations did not.

Version 1.2.29 bounds the failed recovery path. If three audio recovery attempts have no intervening successful audio completion, it saves the first audio fault snapshot to NVS and restarts the MCU once. A retained RTC flag prevents an immediate repeated-reboot loop. If the same fault persists after restart, the firmware stops cycling USB every ten seconds, detaches the unusable USB device, and reports `recovery_exhausted` through `/api/guard`. After two minutes mounted with no recovery, the restart allowance resets for a future independent incident. This is containment, not a USB driver root-cause fix. The NVS fault snapshot is only written on escalation, so routine traffic causes no flash wear.

**1.2.30 correction:** the saved incident advanced `audio_completed` by about 50 over 50 recovery cycles, roughly one packet per failed re-enumeration. Therefore even a positive completion delta cannot by itself count as recovery. The escalation now requires at least 100 completed packets between stalled recovery attempts; smaller deltas keep the consecutive-failure count rising. This is a threshold for sustained transfer progress, not a claim that 100 packets proves overall health.

Validation: 1.2.30 built and booted by OTA, with BLE connected and no new USB recovery. WinMM capture passed 10 open/capture/close cycles; each captured 40–44 KB and completed over 630 USB packets, with zero recovery and zero failed audio submissions. Manual voice-key release on 1.2.30 and the actual repeated-stall branch remain unverified. Extended use should monitor `usb_recoveries`, `recovery_exhausted`, and the persisted fault field. The actual repeated-stall branch cannot be verified without a reproduced fault or controlled hardware fault injection. Do not claim elimination from a short clean test.
